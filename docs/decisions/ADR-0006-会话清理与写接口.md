# ADR-0006 · 会话清理与写接口

> 用户确认后，Uniflo 先把会话写成精简归档，再把源文件移入系统回收站；这是"只读 harness 数据"的两个例外之一（另一个是 ADR-0007 的 `uniflo setup`）。网关因此有了写接口，全部写接口共用一道比读接口更严的守卫；本 ADR 修订 ADR-0004 中"网关只读"的条款。

状态：`accepted` · 更新：2026-10-09

## 背景

- harness 会话只增不减（本机约 17 GB），大头是工具输出、图片和 base64。用户想释放空间，但不想丢掉历史、检索和用量统计。
- 两条既有约束挡着：`AGENTS.md` 的"只读 harness 数据"，以及 ADR-0004 的"网关只读，没有写接口"。
- 写接口比读接口危险：任何网页都能向 `127.0.0.1` 发 `POST`；`text/plain` 之类的"简单请求"不触发 CORS 预检，响应读不到也已经执行了（CSRF）。

## 决策

### 清理是带约束的例外

- **只走"计划 → 确认 → 执行"**：`POST /v1/cleanup/plan` 只读元数据、不改任何东西；执行只接受 10 分钟内的 `plan_id`（`uniflo-core::cleanup::PLAN_TTL`），每个计划只执行一次。CLI `uniflo clean` 先打印计划，交互终端要确认，非交互必须带 `--yes`。
- **只动适配器声明的目标**：`Adapter::cleanup_targets` / `LineDecoder::cleanup_targets`，默认 `None`（不支持）。只有一个文件对应一个会话的 JSONL/JSON harness 声明：会话主文件加该会话独占的附属文件或目录。SQLite 型和多会话共用文件的 harness 不声明。清单见 `docs/adapters.md#会话清理`。
- **不可清理**：状态为 work、有存活进程、是另一个会话的子代理（随父会话整棵子树清理）、目标不在该 harness 的根目录内、目标是符号链接或共享硬链接、目标同时属于另一个会话（同一源或目录下有子树之外的会话）。
- **先归档、后移动，永不删除**：执行时逐个会话重新校验目标与文件戳（大小、mtime、inode）→ 读文件算 SHA-256 → 写精简归档（临时文件 + fsync + rename）→ 清单写进 `cleanup.log.jsonl` 并 fsync、写 `index.json` → 再比一次文件戳 → 移入系统回收站 → 持久化墓碑。任何一步失败，该会话的文件留在原处；不回退为永久删除。只移走一部分时（`trash_partial`）保留归档，没移走的文件重新作为源读取。
- **精简归档**：`<数据目录>/archive/<harness>/<id>.jsonl.zst`，zstd（`ruzstd`，纯 Rust）压缩的 JSONL：第一行 `Session`（`archived: true`，`source` 指向归档文件），之后是去重后的全部 `Event`。user / assistant / reasoning / system 正文每条最多 16 KiB，工具参数与输出各最多 2 KiB，≥ 256 字符的 base64 段替换为 `[binary omitted: N bytes]`，被截的事件标 `truncated: true`；usage 事件原样保留，缺 `model` 的按用量账本的规则补上，因此费用与清理前一致。
- **归档会话照常可用**：列表、详情、事件、全文检索、`/v1/usage` 都从归档读取；`Session.archived = true`、状态 idle。用户从回收站把源文件还原后，以源文件为准、`archived` 消失，归档文件保留到用户执行 `DELETE /v1/archive/{key}` / `uniflo archive rm`。
- **墓碑**：`archive/tombstones.json` 只记 `{path, key, at}`。墓碑下的路径不作为源读取，除非内容与清理日志里的清单一致（大小 + SHA-256，即用户从回收站还原）——这时撤销墓碑。这样旧位置残留的副本、同步工具写回的旧文件不会让会话重复出现。
- **回收站**：`trash` crate 5.x。macOS 用 `NSFileManager` 方式，不弹 Finder 自动化授权（launchd 守护进程无法应答该弹窗），代价是 Finder 的"放回原处"可能不可用，从废纸篓拖回原位置即可还原；Linux 为 freedesktop 规范，Windows 为回收站。测试只注入回收站目录（`DirTrash`，或 `UNIFLO_TRASH_DIR`）；设了 `UNIFLO_HOME` 而没设 `UNIFLO_TRASH_DIR` 时一律拒绝移动（`NoTrash`），测试和沙箱碰不到用户真实的回收站。

### 写接口安全边界

所有写接口（本 ADR 的清理与归档接口，以及之后的"打开终端"等接口）共用一道写守卫：网关守卫对 `GET` / `HEAD` / `OPTIONS` 以外的每个请求调用 `uniflo-gateway::write::check`，在读守卫（ADR-0004）之外再要求：

| 条件 | 说明 |
|---|---|
| Host 是回环名 | `localhost` / `127.0.0.1` / `::1` / `*.localhost`；`--allow-host` 只放宽读接口，写接口不认 |
| Origin | 不带，或为回环 http(s) 来源，或在 `--cors-origin` 中逐字列出；`*` 对写接口不生效 |
| `X-Uniflo-Write: 1` | 自定义请求头让浏览器必须先过 CORS 预检，外站页面无法以简单请求触发写操作 |
| token | 配置了 token 时必须携带；写请求缺 token 返回 403（读请求仍为 401） |

任一条件不满足返回 403。守护进程以 `--read-only` 启动时，全部写接口返回 403，`/v1/health` 给出 `read_only: true`。

### 对 ADR-0004 的修订

ADR-0004 的"网关只读，没有写接口"改为：网关默认只读；写接口只有本 ADR 及之后 ADR 明确列出的几类，全部经过写守卫，可用 `--read-only` 整体关闭。ADR-0004 其余条款不变。

实施状态：已落地。核心 `crates/uniflo-core/src/{cleanup,archive}/`、`engine_archive.rs`；网关 `crates/uniflo-gateway/src/{write,cleanup}.rs`；CLI `crates/uniflo-cli/src/clean.rs`；测试 `crates/uniflo-gateway/tests/cleanup.rs`、`crates/uniflo-cli/tests/clean.rs`、`crates/uniflo-adapters/tests/cleanup.rs`。

## 否决项

- 直接永久删除：不可撤销，误判即丢数据。
- 不留归档就移走：历史、检索和用量统计随之消失，违背"释放空间但不丢信息"。
- 归档保留原始文件（或整份压缩原文件）：图片和 base64 照样占空间，省不下多少；归档格式也会耦合各家 harness 的私有格式。
- 归档写在 harness 目录里：违反只读契约，也会被 harness 自己的清理逻辑删掉。
- macOS 用 Finder（AppleScript）方式移入废纸篓：能"放回原处"，但首次需要自动化授权弹窗，后台守护进程无人应答。
- 用 `GET` 或表单 `POST` 承载写操作、只靠 CORS：都能被外站页面以简单请求触发。
- 让 `--allow-host` 与 `--cors-origin *` 也放开写接口：局域网或任意网页即可移动用户文件。

## 后果

- `AGENTS.md` 的"只读 harness 数据"契约写明此例外及其约束；`docs/api.md`、`docs/schema.md`、`docs/search.md`、`docs/adapters.md`、`docs/architecture.md` 同步。
- 数据目录多出 `archive/`。精简后的大小取决于工具输出与二进制的占比；验收上限为源文件的 20%，计划阶段按 10% 预估（`ARCHIVE_RATIO`），执行结果给出实际大小。
- 墓碑存在期间，若 harness 在同一路径写出内容不同的新文件，它不会被读取，直到用户删除该归档（`archive rm` 同时撤销根会话的墓碑）。目前首批 harness 的会话路径都含唯一 id，不会复用。
- 新增写接口必须用写方法（`POST` / `DELETE` 等），由网关守卫按方法统一套用写守卫，并在 `docs/api.md#写接口` 登记；不得用 `GET` 做写操作。
- 新依赖 `trash`、`sha2`（已批准）。

## 复议触发

- 用户需要永久删除，或需要清理 SQLite 型 harness 的会话。
- 某个 harness 会复用会话路径，或在会话目录里存放用户自己的产物。
- Linux / Windows 回收站行为与 macOS 不一致，导致还原后无法被识别。
- 需要远程或多用户写访问：改为正式鉴权（同 ADR-0004 的复议触发）。
