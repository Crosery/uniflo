# ADR-0009 · 预编译分发与自升级

> crates.io 仍是主渠道；GitHub Releases 附加 5 个目标的预编译包、`SHA256SUMS`、安装脚本和 cargo-binstall 元数据，`uniflo update` 按安装方式升级。修订 ADR-0005 中"只发 crates.io、只用 `cargo install` 升级"两条。

状态：`accepted` · 更新：2026-10-30

## 背景

`cargo install uniflo` 要求本机有 Rust 工具链，并且要从源码编译几分钟（含 bundled SQLite 的 C 代码）。没有 Rust 的用户装不上，而 ADR-0005 的 `uniflo update` 默认所有安装都来自 cargo。需求 D14 定了做法：GitHub Releases 发 5 个目标的二进制，提供 `install.sh` / `install.ps1` 和 cargo-binstall 元数据，`uniflo update` 按安装方式升级，不做 Homebrew。D19 要求 crates.io 仍是主渠道。

约束：

- 不新增 HTTP / TLS / 压缩依赖。下载走系统 `curl`，解包走系统 `tar`，Windows 上走 PowerShell `Expand-Archive`。只用已批准的 `sha2` 做校验（D13）。
- 依赖方向不变：安装方式识别和自升级放在 `uniflo-core::install`，CLI 只做接线和提示。
- 测试不能碰用户真实的安装和守护进程。

## 决策

- **发布产物**（`.github/workflows/release.yml`）：
  - 原 `publish` job（verify → crates.io）不动。`build` job 跟在它后面，按矩阵构建 `aarch64-apple-darwin`、`x86_64-apple-darwin`（都在 `macos-latest` 上，后者交叉编译）、`x86_64-unknown-linux-musl`（`ubuntu-latest`）、`aarch64-unknown-linux-musl`（`ubuntu-24.04-arm`）和 `x86_64-pc-windows-msvc`（`windows-latest`）。两个 musl 目标用 `musl-tools` 的 `musl-gcc` 编 SQLite。
  - 每个目标用 `scripts/package.sh` 打包，产物为 `uniflo-<version>-<target>.tar.gz`（Windows 为 `.zip`）。包里只有一个目录 `uniflo-<version>-<target>/`，内含可执行文件、`LICENSE` 和 `THIRD_PARTY_NOTICES.md`。
  - `release` job 等 5 个包都到齐后生成 `SHA256SUMS`，再用 `gh release create` 把这些包、`SHA256SUMS`、`install.sh` 和 `install.ps1` 一起上传到 tag 对应的 Release。tag 含 `-` 时加 `--prerelease`。
  - tag 版本必须等于 `Cargo.toml` 的版本，不一致时 `build` 失败。
- **顺序**：crates.io 先发，二进制随后。主渠道不会因为某个目标构建失败而被卡住。代价是：crates.io 已经有新版本、但 Release 资产还没传完的那几分钟里，binary 安装的 `uniflo update` 会因下载失败而中止，可执行文件不受影响，稍后重试即可。
- **安装脚本**：
  - `scripts/install.sh`（POSIX sh，macOS / Linux）：
    - 按 `uname` 选择目标。Rosetta 下的 shell 在 Apple 芯片上仍装 arm64 版；Linux 一律装静态 musl 版。
    - 版本由 `UNIFLO_VERSION` 指定。不指定时读 `<base>/latest/download/SHA256SUMS`，从里面列出的包名得到最新正式版的版本号；GitHub 的 latest 不含预发布。
    - 下载包和对应版本的 `SHA256SUMS`，用 `shasum -a 256` 或 `sha256sum` 比对。
    - 解包后先运行一次 `--version`，必须输出 `uniflo <version>`。
    - 以上全部在临时目录里完成；任何一步失败都直接退出，非 0 退出码，不创建安装目录，也不写 `install.json`。之后才在安装目录里暂存，再改名到位，正在运行的旧进程不受影响。
    - 最后写 `<配置目录>/install.json`：`{method:"binary", target, version, path}`，配置目录的推算与 `uniflo_core::paths::config_dir()` 一致。
    - stdout 是终端且 `/dev/tty` 可读时，用 `/dev/tty` 作输入运行 `uniflo setup`；`curl | sh` 时 stdin 是管道，所以要从 `/dev/tty` 读。`--no-setup`、`UNIFLO_NO_SETUP=1` 或非终端时跳过。
  - `scripts/install.ps1` 行为相同：用 `Get-FileHash` 校验，默认装到 `%LOCALAPPDATA%\Programs\uniflo`。`install.json` 不写 BOM，因为 serde_json 不接受 BOM。
  - 两个脚本都用 `UNIFLO_RELEASE_BASE_URL` 覆盖发布根地址，测试用它指向本地服务。
- **cargo-binstall**：`crates/uniflo-cli/Cargo.toml` 的 `[package.metadata.binstall]` 指向同样的包名和目录（Windows 覆盖为 `.zip`）。包名里直接写扩展名，不用 `{ archive-suffix }`，因为它在 tgz 格式下展开为 `.tgz`。`scripts/check-dist.mjs`（在 `scripts/verify.sh` 中运行）检查以下几处保持一致：
  - 用 `cargo metadata` 读出模板并展开；
  - 工作流的目标列表；
  - `package.sh` 实际打出的包；
  - `uniflo_core::install::asset_name`。
- **安装方式识别**（`uniflo_core::install::detect`，路径都先解析符号链接再比较）：
  - `install.json` 里的 `path` 就是当前可执行文件 → `binary`；
  - 当前可执行文件直接位于 `$CARGO_HOME/bin` 或 `~/.cargo/bin` → `cargo`；
  - 其他 → `unknown`，例如源码构建、拷贝的文件、包管理器安装。
  - `uniflo update --check --json` 在原有字段之外输出 `method`。
- **升级**：
  - `cargo`：沿用 `cargo install uniflo --force --version <v>`。
  - `binary`（`uniflo_core::install::upgrade_binary`）：
    1. 在私有临时目录里，用 `curl -fsSL` 下载 `<base>/download/v<v>/` 下的包和 `SHA256SUMS`。
    2. 用 `sha2` 比对。
    3. 解包，并确认新文件的 `--version` 正确。
    4. 把新文件复制到可执行文件旁边暂存，再改名替换。Unix 上直接改名覆盖，运行中的进程保留旧 inode。Windows 上运行中的 exe 不能覆盖，但可以改名：先把它改名为 `uniflo.exe.old`，再放入新文件；第二步失败时把 `.old` 改回原名。`uniflo` 每次启动时删除残留的 `.old`。
    5. 成功后更新 `install.json` 的 `version`。
    - 下载、校验、解包、版本自检、替换中任何一步失败，原可执行文件都不变，退出码非 0，并给出原因。
  - `unknown`：打印两种升级方式（`cargo install …` 与一行安装脚本），不做任何改动。
  - `--pre` 语义不变：只在显式指定时装预发布版。
- **升级后**：
  - macOS 上，只有当已加载的 launchd 服务 `com.crosery.uniflo` 运行的程序（`launchctl print` 的 `program`）就是刚升级的这个可执行文件时，才执行 `launchctl kickstart -k`。服务运行的是另一份可执行文件时，重启它也换不成新版本，所以只打印说明。读不出 `program` 时同样不重启。
  - 然后进入 agent-access 定义的 setup 收尾流程（`setup::after_update`），命令里传入升级前解析出的可执行文件路径；Linux 上文件被替换后，`current_exe()` 会带 ` (deleted)` 后缀。
- **校验策略**：完整性依赖 HTTPS 下的 GitHub Release 与同源的 `SHA256SUMS`。它防的是传输损坏、截断和错包，不防发布账号或仓库被攻破。
- **不签名、不公证**：经 `curl` 或 `Invoke-WebRequest` 下载的命令行程序不会带隔离属性（`com.apple.quarantine`），Gatekeeper 不拦截，所以不需要 Apple 开发者证书和公证流程。`package.sh` 在 macOS 上用 `--no-xattrs --no-mac-metadata` 打包，不把构建机的扩展属性带进包里。
- **不做 Homebrew**（D14）：维护 tap、formula 和 bottle 是另一条发布链路，收益不抵成本。
- **第三方许可证**：`THIRD_PARTY_NOTICES.md` 的「Rust crates」一节由 `scripts/third-party-notices.mjs` 按 `cargo metadata` 生成：编进二进制的全部 crate，含所有目标平台，以及它们随包附带的许可证文本，相同文本只列一次。`verify.sh` 用 `--check` 检查它是否过期；网页演示的第三方资源另起一节。

## 命令行提醒（2026-10-25）

- 终端里运行的命令（不含 `daemon`、`mcp`、`setup`、`skill`、`context`、`update`，也不含带 `--json` 的调用）结束时，若缓存里已有比当前版本新的正式版，向 stderr 打印一个小框，提示运行 `uniflo update`；只有预发布版更新时只提示一行 `--pre`。
- 只在 stdout 和 stderr 都是终端、且没有 `CI`、`UNIFLO_NO_UPDATE_CHECK` 时出现，管道、hook 与 agent 读到的输出不变。
- 版本信息缓存在缓存目录的 `update-check.json`（`checked_at`、`tried_at`、`latest`、`prerelease`）：超过 1 小时没有成功检查才在后台线程里查一次 crates.io 稀疏索引（沿用 `uniflo_core::update::check`，系统 `curl`），失败后 10 分钟内不再试；命令结束时最多等这个线程 1.5 秒，没等到就按旧缓存提醒。这与守护进程每小时一次的检查互不依赖。

## 镜像与地区（2026-10-30）

中国大陆的用户反复遇到 `crates.io index fetch failed`：curl exit 7（连不上）、exit 28（15 s 超时）。原因是更新检查只问 `index.crates.io` 一个源。本机实测 GitHub Release 的包下载也会连接超时，同一时刻国内镜像可在 1 s 内返回。

- **地区**：只看本机时区，不联网查 IP。
  - Unix 读 `TZ`，再读 `/etc/localtime` 的链接目标或 `/etc/timezone`；Windows 用 `tzutil /g`。
  - `Asia/Shanghai`、`Asia/Chongqing`、`Asia/Harbin`、`Asia/Urumqi` 等中国大陆时区和 `China Standard Time` 算中国大陆，其他都算海外。
  - `UNIFLO_MIRROR=cn|official` 覆盖判断。
  - 判断错了只会慢一点，不会查不到：两组源都会被问到。
  - 实现在 `uniflo_core::mirror`。
- **版本检查**（`uniflo_core::update`）：
  - 两组源：官方 `index.crates.io`；国内 rsproxy.cn、中科大。中国大陆先问国内组，海外先问官方组。
  - 首选组 2 s 内没有回答或全部失败，就同时问另一组。
  - 第一个回答到达后，再等其他源 0.8 s，取所有回答中最新的版本，所以同步滞后的镜像不会把新版本藏掉。
  - 清华 TUNA 在发版 3 小时后仍落后一个版本，上交 SJTU 没有稀疏索引，两者都不列入。
  - 单个请求连接超时 5 s，整次检查最多 12 s。
  - `UNIFLO_UPDATE_INDEX_URL` 仍然只用它一个源。
- **cargo 安装的升级**：
  - 中国大陆时区，且 `$CARGO_HOME/config.toml`（或 `config`）里没有 `replace-with` 时，`cargo install` 加 `--config` 把 crates.io 换成 `sparse+https://rsproxy.cn/index/`。
  - 用户自己配置过源替换就不动它。
- **发布包下载**（`uniflo update` 的 binary 方式和两个安装脚本）：
  - 顺序是 GitHub，然后 `https://ghfast.top/<GitHub 地址>`，再然后 `https://gh-proxy.com/<GitHub 地址>`。
  - 单个源连接超过 8 s，或连续 20 s 低于 10 KB/s，就换下一个。
  - `SHA256SUMS` 按同样顺序取，GitHub 能回答时校验值总是来自 GitHub。
  - `UNIFLO_RELEASE_BASE_URL` 仍然只用它一个源。
- **代价**：
  - 加速站是第三方服务，可能下线。
  - GitHub 完全不可达时，包和校验值都经同一个加速站取得，只能防传输损坏，不能防加速站篡改。
  - 需要防篡改时按「复议触发」给 `SHA256SUMS` 加签名。
- **否决**：
  - 联网查 IP 归属地：暴露用户 IP，定位服务在国内同样可能不可达。
  - 每次都并发问所有源：请求数翻倍，换来的延迟收益只在首选组慢时才有，而对冲已经覆盖了这种情况。
  - 自建国内镜像：需要另开账号和 CI 密钥，暂缓。

## 否决项

- 引入 `reqwest` / `ureq` + `flate2` / `tar` / `zip` crate：新增生产依赖，体积和审计面都会变大，而系统工具已经够用（同 ADR-0005）。
- 从 crates.io 拉源码，在本机编译后替换：等于 `cargo install`，要求用户有工具链，正是要解决的问题。
- 用 GitHub API（`api.github.com/repos/.../releases/latest`）取最新版本：匿名调用有速率限制，返回的 JSON 在 sh 里也不好解析。`releases/latest/download/SHA256SUMS` 是一次普通下载，还顺带给出了校验值。
- 版本号不进包名（`uniflo-<target>.tar.gz`）：`latest/download/` 能直接下载，但 cargo-binstall 和固定版本的安装就没法区分版本，旧链接也会悄悄指向新版本。
- 无条件 `kickstart` launchd 服务（ADR-0005 的做法）：服务运行的不是被升级的那份时，只会无谓地打断守护进程；测试里这样做还会重启用户真实的服务。
- 守护进程后台自动安装升级：不在需求范围内，仍然是"检查 → 提示 → 手动 `uniflo update`"。

## 后果

- 发版多出 5 个构建 job 和一次 Release 上传。真实的跨平台构建和上传只有推送 tag 后才能在 CI 上验证；本机只验证当前平台：本机构建的 release 包经本地 HTTP 服务完成安装、篡改中止、自升级（`scripts/dist-e2e.sh`）。
- `uniflo update` 会经系统 `curl` 下载发布包。这一步只在用户显式运行 `uniflo update` 时发生，作用和 `cargo install` 的下载相同，请求里不带会话数据。后台的联网仍然只有版本检查和价格同步两处。
- 新增环境变量：`UNIFLO_RELEASE_BASE_URL`（发布根地址，设置后只用它）、`UNIFLO_UPDATE_INDEX_URL`（更新检查用的稀疏索引地址，设置后只用它）、`UNIFLO_MIRROR`（`cn` / `official`，覆盖按时区的选择），以及安装脚本用的 `UNIFLO_VERSION`、`UNIFLO_INSTALL_DIR`、`UNIFLO_NO_SETUP`。
- 依赖变化后要重新生成 `THIRD_PARTY_NOTICES.md`，否则 `scripts/verify.sh` 失败。
- Windows 的 `.old` 改名与清理逻辑有跨平台单测（`uniflo_core::install` 的 `Swap::Aside`），真实 Windows 运行未验证；`install.ps1` 未在 PowerShell 中运行过。

## 复议触发

- 出现需要签名验证的分发渠道（例如企业内网镜像），或 GitHub Release 资产需要防篡改保证时，考虑给 `SHA256SUMS` 加签名（minisign / Sigstore）。
- macOS 开始对 curl 下载的程序也强制检查，或用户要求 `.pkg` 安装器时，重新评估公证。
- 某个目标的 runner 不可用（例如私有仓库没有 `ubuntu-24.04-arm`）时，改用交叉编译工具链。
