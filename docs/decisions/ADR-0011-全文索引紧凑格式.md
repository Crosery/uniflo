# ADR-0011 · 全文索引紧凑格式：分层存储

> 近 7 天活动过的会话保留 ADR-0008 的带位置 FTS5 格式（热层），更早的会话按会话切成约 64 KB 的块，zstd 压缩后存放，另建一份只记块号的 trigram 索引（冷层）。查询先算热层，再按会话从新到旧核验冷层候选块，一旦更早的会话不可能进入这一页就停下。升级时直接从旧索引转换并删除旧文件。本机升级实测从 6.10 GB 降到 1.81 GB（−70%）；120 条查询与原格式对比，差异都有出处（见「落地验收」）。

状态：`accepted` · 更新：2026-10-24

实施状态：已实施（`crates/uniflo-search/src/fts/`），真实数据验收见下文「落地验收」与 `notes/2026-10-24-worklog.md` 第 13 节。

## 背景

ADR-0008 的索引在本机是 5.77 GB，有用户反馈占用太大。用只读 `dbstat` 拆开看（1,396,479 条事件，正文 1.28 GiB）：

| 部分 | 大小 | 占比 |
|---|---|---|
| `docs_fts_data`（trigram 倒排，`detail=full`，含位置） | 3.92 GB | 68% |
| `docs`（原文 + 元数据） | 1.76 GB | 31% |
| 其余（autoindex、docsize） | 0.08 GB | 1% |

对 trigram 来说，每个字符都是一个 token，所以位置信息是大头，倒排约为正文的 3 倍。

用户的使用方式：
- 查得最多的是最近的会话，查远一点的会话可以稍慢。
- 要尽量省空间，升级时就把空间省下来。
- 不能丢信息，能搜到的内容和结果都不能少。

约束同 ADR-0008：
- 不新增生产依赖，只有 bundled `rusqlite` 和 `ruzstd`。
- 子串语义、bm25 × 近因排序、每会话 3 条、翻页、片段、短词扫描保持不变。

另外，ADR-0008 的标签含 Uniflo 版本，每次升级都整份重建，本机约 14 min。它的复议触发里写了"索引大小成为用户痛点，或升级时重建不可接受"，现在两条都成立。

### 为什么"去掉位置"会让高频词变慢

上一版提议的方向 1 去掉了位置（`detail=none`），倒排只能回答"哪些事件同时含有这几个 trigram"：
- 不知道这几个 trigram 是否相邻，所以 ≥ 4 字符的词要读原文核验。
- 不知道出现了几次，而 bm25 要用词频。

于是每条候选事件都要取出原文、解压、扫一遍。`the` 有 34 万条候选：取原文约 6 µs，解压约 15 µs，单线程要 9.8 s。罕见词只有几十条候选，所以反而更快。慢不在算法本身，而在要核验的候选数。

## 实测

原型读本机真实索引的只读副本，Apple M4 Pro（14 核），只打印大小、计数和耗时。

### 正文按会话最后活动时间的分布

| 距今 | 正文 | 累计 |
|---|---|---|
| < 7 天 | 231 MB | 16.2% |
| < 14 天 | 157 MB | 27.1% |
| < 30 天 | 525 MB | 63.8% |
| < 60 天 | 398 MB | 91.6% |
| 更早 | 120 MB | 100% |

### 每字节正文占用的磁盘

- 热层（现有格式，用最近 30 天的会话实建）：913 MB 正文 → 3,653 MB，即 4.00 字节/字节。
- 冷层（全部 1.43 GB 正文实建，64 KB 块）：973 MB，即 0.68 字节/字节。
  - 其中块数据（zstd 正文 + 元数据）679 MB，块级 trigram 索引 292 MB。
  - 建成耗时：单线程写入 151 s，optimize 加 VACUUM 15 s。

块大小与压缩率（`ruzstd` 只有 `Fastest` 一档，0.9.1 仍然如此，也不支持带字典压缩，2026-10-24 核对）：

| 块 | 16 KB | 32 KB | 64 KB | 128 KB | 256 KB |
|---|---|---|---|---|---|
| 压缩后 | 699 MB | 661 MB | 628 MB | 602 MB | 598 MB |
| 压缩比 | 2.05 | 2.16 | 2.28 | 2.38 | 2.39 |

完全相同的事件正文占 9.3%（133 MB），这次不做跨会话去重。

### 按热层天数估算本机体积

| 热层 | 热层正文 | 合计 | 相对现在 |
|---|---|---|---|
| 7 天 | 231 MB | ≈ 1.74 GB | −70% |
| 14 天 | 388 MB | ≈ 2.26 GB | −61% |
| 30 天 | 913 MB | ≈ 4.0 GB | −31% |
| 全部冷层 | 0 | 0.97 GB | −83% |

使用时间更均匀的用户，7 天的占比更小，节省更接近 −80%。

### 冷层查询

候选块全部核验（每块解压后逐条事件做子串匹配），命中数与现有 FTS5 一致；少数差几条，是测量期间守护进程又写入了新事件。

| 词 | 现在（FTS5 全部打分） | 候选块 | 冷层全核验 1 线程 | 8 线程 |
|---|---|---|---|---|
| `the` | 758 ms | 26,444 | 9,944 ms | 1,319 ms |
| `error` | 1,104 ms | 24,345 | 10,967 ms | 1,380 ms |
| `return` | 871 ms | 23,860 | 9,340 ms | 1,254 ms |
| `uniflo` | 118 ms | 1,812 | 706 ms | 92 ms |
| `cargo test` | 199 ms | 1,984 | 909 ms | 126 ms |
| `deploy script` | 205 ms | 5,558 | 2,343 ms | 348 ms |

### 提前终止

排序分数 = bm25 × 近因权重：
- bm25 每个词的 tf 部分不超过 k1 + 1 = 2.2。
- 近因权重随会话变旧单调下降。

所以，对一个最后活动时间为 t 的会话，它的分数不会超过 Σ idf × 2.2 × 近因(t)。

做法是按会话从新到旧核验冷层。一旦这一页第 `offset + limit` 名的分数已经严格大于下一个会话的这个上界，后面的会话都不可能进页，可以停止。这样停止不改变结果。

用真实分数模拟，统计需要核验的冷层压缩字节：

| 词类 | 热层 7 天：中位 / p95 / 最大 | 14 天：中位 / p95 / 最大 |
|---|---|---|
| 常用词 11 个 | 23 / 42 / 99 MB | 0 / 21 / 81 MB |
| 随机抽样的 ASCII 词 44 个 | 42 / 170 / 380 MB | 10 / 141 / 328 MB |
| 中文词 6 个 | 0 / 0.6 / 3.1 MB | 0 / 0.6 / 2.6 MB |

- `the`、`error` 一个冷块都不用开：热层里已有足够多高分会话。
- 最难的是中频词：热层里凑不满一页，又在很多旧会话里出现。

### 落地验收（2026-10-24，本机真实数据，只读副本）

- 升级：旧索引 6.10 GB + 59 MB WAL；守护进程 0.2 s 开始服务 HTTP，后台转换 6,290 个会话用时 373 s，转换期间检索正常（8–495 ms）；`reclaimed_bytes` = 6,100,180,992。
- 转换后版本刷新约 225 s，冷块 23,137 个一个未重写（内容指纹）。
- 体积：主库 1,810 MB（停机 checkpoint 后），其中热层 975 MB、冷层 902 MB，比旧格式 −70%。
- 与旧格式对比 120 条查询：同一批会话 113 条、顺序一致 109 条、命中一致 106 条。其余差异都有出处：旧索引没跟上源文件（核对源文件确有该词）、分数近似相等的相邻会话换位、多词查询的 idf 只取热层、30 条 `total` 为下限。
- 延迟：p50 132 ms（旧格式 118 ms），最慢 3.5 s（旧格式 9.7 s）；最慢的是冷层中频词翻页（`error` 带 offset 2.8 s）。

## 决策

### 分层

- **热层** = ADR-0008 的 `docs` + `docs_fts`（`detail=full`），放会话 `updated_at` 在 `hot_days` 天内（默认 7）的会话。
  - `uniflo daemon --fts-hot-days <n>` 可以改天数。
  - 实时写入只进热层。
- **冷层** = 其余会话。一个会话整体只在一层里。
  - `blk(bid INTEGER PRIMARY KEY AUTOINCREMENT, sid, first, last, rows, kinds, tokens, bytes)`：块目录。
  - `blk_data(bid, z)`：一个 zstd 帧，内容为逐行元数据（行号、`event`、`ts`、`pos`、长度）加正文。
  - `blk_fts = fts5(text, content='', contentless_delete=1, detail=none, tokenize='trigram case_sensitive 0')`：以块号为 rowid，正文用 `\u{1}` 连接。
  - 块按会话切分，一块不超过 64 KB；单条超长事件独占一块。
  - 行号沿用 `sid << 32 | seq << 3 | kind`，块号 `AUTOINCREMENT` 不复用，缓存可以安全地以块号为键。
- **统计**：`meta` 里维护 `hot_rows`、`hot_tokens`、`cold_rows`、`cold_tokens`、`cold_gen`，与数据写入在同一事务里更新。
  - token 数 = 字符数 − 2（不足 3 个字符时为 0），与 trigram 分词一致，测试对照 FTS5 的 docsize。

### 写入

- **降温**：写线程空闲时，把 `updated_at` 早于截止时间、不在 pass 中的热层会话整体搬到冷层：
  - 按行号顺序切块，写 `blk` / `blk_data` / `blk_fts`；
  - 删掉热层的行；
  - 递增 `cold_gen`。
  - 每次提交的工作量有界，并像回填一样节流。
- **升温**：
  - 冷层会话收到写入（实时事件、对账 pass、归档会话的 `index_session`）时，先把它的块解压回热层，行号不变，再照常 upsert。
  - 例外：对账 pass 开始时会话仍早于截止时间，比如升级后的刷新，见下。这时在内存里收齐该会话的行，与现有块的内容指纹比较，相同就只记进度，不同才重写这个会话的块。
  - 指纹只看每行的内容（kind、`event`、`ts`、`pos`、正文），与行号和行的先后无关：降温和迁移按到达顺序编号，全新 pass 按从新到旧编号，同样的内容也要判为相同。用 FNV-1a 逐行哈希后相加，跨构建稳定（指纹存在库里）。
- **全新构建**：
  - 早于截止时间的新会话，pass 在内存里收齐行，直接写冷层；
  - 不先进热层，所以首建时文件不会先涨到旧格式的大小。
- **删除**：同时删两层的行和块。
- **空间回收**：新文件建库前设 `auto_vacuum=INCREMENTAL`；空闲时空闲页超过 5% 就分步 `incremental_vacuum`，文件跟着变小。

### 查询

- **核验**：冷层候选块 = `blk_fts` 对所有正向词的 trigram 求 AND（表达式作为参数绑定），再按会话过滤器筛掉；块号经缓存的块目录映射到会话，一个会话只解压它的候选块。
  - 解压后逐条事件判断，规则与 FTS5 trigram 一致：每个正向词都是折叠大小写后的子串，排除词不出现，短词按 SQLite `LIKE` 的 ASCII 大小写不敏感匹配。
  - 折叠表启动时用 FTS5 自己的 trigram 分词器在内存表里探测得到，不用 Rust 的 `to_lowercase` 近似。
- **打分**：冷层在 Rust 里用 FTS5 bm25 的同一公式。
  - 词频 = 子串出现次数，允许重叠；文档长度 = token 数。
  - 平均文档长度用两层合计。
  - 热层的辅助函数改为接收同样的统计量，所以两层分数可以直接比较。
- **IDF**：用热层的命中比例计算，`idf(hot_rows, 热层命中行数)`；热层为空时取 1。
  - 单个词时 IDF 是公因子，不影响顺序。多个词时它是各词的权重，按近期数据估计。
  - 这是相对 ADR-0008 唯一的排序语义变化。分数与查询是否提前停止无关，翻页顺序固定。
- **相关度排序**：
  - 热层照旧全部打分。
  - 冷层候选会话按 `updated_at` 从新到旧分批并行核验（线程数为 CPU 数，最多 8；每批每线程一个会话），批内每个会话入批前都先过上面的上界判断。压缩数据由查询自己的读事务取出，工作线程只解压和匹配，所以全部核验都在同一个快照上。
  - 页确定之后，在 250 ms 预算内继续对剩下的冷层候选会话做"至少一条命中"的核验，`total` 因此通常是精确值。
  - 预算用完时，`total` 为下限，并给出 `scanned_until`。这个字段原有的语义不变，只是不再限于短词扫描。
- **短词扫描**：从最近活动的会话往回扫，冷层会话解压后在 Rust 里匹配；2 s 预算、`partial`、`scanned_until` 的语义不变。
- **片段**：冷层命中从解压后的正文截取，用与热层相同的高亮规则；非 ASCII 的大小写差异按折叠表定位。

### 缓存

| 层 | 内容 | 失效 |
|---|---|---|
| 热层 | 最近 7 天的会话，带位置倒排，常用词不用读原文 | 降温时移出 |
| 块缓存 | 解压后的块，LRU，默认 64 MB | 块号不复用，随 LRU 淘汰 |
| 块目录 | `blk` 的块号 → 会话、行号范围 | `cold_gen` 变化 |
| 冷层核验缓存 | 每组词与 kinds 已核验会话的匹配行（行号、长度、各词次数），最近 16 组、合计最多 256k 行；单个会话超过 16k 行匹配时只记是否命中 | `cold_gen` 变化 |
| 系统页缓存 | 启动或合并后预读 `docs_fts_idx`、`docs_fts_docsize`、`blk_fts_idx`、`blk` | — |
| 折叠表 | 启动时探测一次 | — |

翻页和重复查询直接复用已核验的会话，不再解压。复用时按当前的 IDF 和平均文档长度重新打分：热层统计随每次写入变化，缓存分数会与重新核验的结果不一致；缓存匹配行的事实就没有这个问题。会话过滤器不进缓存键，它只决定看哪些会话，不改变一个会话的核验结果。

### 升级与回收

- **标签**改为 `uniflo-fts/format2/schema{SCHEMA_VERSION}`，文件名 `fts-v2.sqlite`。Uniflo 版本另存在 `meta.version`。
- **版本变化时就地刷新**：保留索引，把所有非归档会话的 `done_upd` 清空，对账照常在后台按从新到旧重读一遍。
  - 搜索不中断。
  - 内容没变的会话不写入（热层 upsert 本来就跳过相同的行，冷层按上面的比较跳过）。
- **从 `fts-v1.sqlite` 转换**：启动时发现旧格式文件，写线程在进入正常循环前直接读它的 `docs` 和 `sess`，按会话从新到旧写入新文件。
  - 近期会话进热层，其余会话直接成块。
  - 每个会话一个事务，中断（守护进程退出）后从没转完的会话继续，旧文件保留到转完。
  - 转完删除 `fts-v1.sqlite` 及 `-wal`、`-shm`，然后照"版本变化"刷新一次。
  - 不用重读 harness 源文件；`Fts::start` 不等转换，守护进程照常启动，已转换的会话即刻可搜。
  - 转换中途磁盘写满时也删掉旧文件：它只是缓存，缺的正是空间；没转完的会话改从源文件补建。
- 旧文件不可读、标签格式不认识时删掉，从源文件全新构建。

### 状态

`FtsStatus` 新增可选字段：
- `hot_days`、`hot_events`、`cold_events`、`cold_blocks`；
- `migrating`：正在从旧格式转换；
- `reclaimed_bytes`：迁移删掉旧格式文件释放的字节数，记在 `meta` 里，重启后仍然显示。

## 否决项

- **方向 1：所有事件都用 `detail=none` 逐条压缩**。体积只降 57%，所有高频词查询都变慢且占多核。分层后近期查询走原格式，冷层用块压缩，体积更小。
- **方向 2：自定义 tokenizer 补词频分桶**。倒排要再大 30–50%，还要通过 FFI 注册 tokenizer。有了"热层先填满一页再按上界停止"，高频词在本机一个冷块都不用开，不必为此付出体积和复杂度。
- **自研块级倒排格式**：块级 varint 倒排实测约 306 MB，与 FTS5 `detail=none` 建在块上的 292 MB 相当。FTS5 已经有增量写、删除、合并和崩溃恢复，自研不划算。
- **冷层存全部数据、热层只作副本**：近期数据要存两份，体积大于分区。
- **按行压缩**：同样的数据按行压缩是 1.50 → 0.92 GB，按 64 KB 块是 1.43 → 0.63 GB。
- **按天数之外的规则分层**（如固定字节预算）：用户的诉求按时间表述，天数也好解释；需要时用 `--fts-hot-days` 调。
- **新增 zstd C 库或带字典的压缩**：要用户批准新增生产依赖。瓶颈在热层体积，不在冷层压缩率。

## 后果

- 本机体积预计 5.77 GB → 约 1.7 GB；冷层每字节正文只占 0.68 字节。
- 升级不再整份重建：
  - 从旧格式转换不读源文件；
  - 之后的版本升级只在后台刷新，搜索不中断。
- 近期会话的查询与现在相同。
- 冷层的中频词查询要解压核验，p95 约 170 MB 压缩数据，比现在慢；结果不变。
- 两份 trigram 分词规则（FTS5 与 Rust 核验）必须一致，靠启动时探测折叠表和逐字符对照测试保证。
- 要同步：
  - `docs/search.md`：存储、性能、`scanned_until`；
  - `docs/schema.md`：`FtsStatus`、`scanned_until`；
  - ADR-0008：表、标签、重建条目指向本 ADR；
  - `AGENTS.md`：索引文件名、大小、首建时间。

## 复议触发

- 冷层查询在实际使用里明显变慢：调大默认 `hot_days`，或给冷层加词频分桶（方向 2）。
- `ruzstd` 支持更高压缩级别或带字典压缩。
- 跨会话重复正文占比明显上升：考虑按内容哈希去重。
