# ADR-0002 · 头尾摘要 + 游标跟随

> 冷启动只读每个源的头尾窗口，之后按字节偏移 / rowid 增量跟随；完整历史按需分页读取。

状态：`accepted` · 更新：2026-10-09

## 背景

单个会话文件可达数百 MB；全量解析所有文件冷启动要数秒，且大部分内容客户端从不查看。

## 决策

- JSONL：头 256 KB 取元数据，尾 256 KB 取最近状态（长行时窗口自动扩大），记录游标 `{offset, size, mtime, state}`。
- 跟随：只读 `offset` 之后的新字节，半行留待下次；文件变短/被重写 → 重新摘要；一次追平超过 16 MB → 走摘要。
- 历史：`before=pos` 反向逐行读取，同 id 去重（保留首个位置、最新内容）。
- SQLite：按 rowid 跟随，未完成的行按主键重读；WAL 签名不变不读。
- 游标与会话快照落盘缓存，重启后只读增量。

实施状态：已落地（`core::jsonl`、`core::cache`、`adapters::opencode` 等）。

## 否决项

- 全量解析后常驻内存：内存与冷启动都不可接受。
- 只读尾部：拿不到标题、cwd、开始时间等头部元数据。

## 后果

- 冷启动全量约 0.9 s（4888 源 / 1.8 GB），有缓存约 0.2 s；单次分页读取个位数毫秒。
- 摘要读取的事件不广播（避免冷启动洪水），只有跟随读取到的新内容进入实时流。
- 依赖"追加写"假设；原地重写的格式（Gemini、Reasonix）通过 id upsert 处理。

## 复议触发

出现大量非追加写、或需要全文检索事件内容时。

- 2026-10-09：全文检索需求触发了本条，结论见 `ADR-0008-全文检索索引.md`。头尾摘要和游标跟随不变；正文由独立的后台线程通过 `Engine::history` 分页读入 FTS 索引，不进入引擎冷启动。
