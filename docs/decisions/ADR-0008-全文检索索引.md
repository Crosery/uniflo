# ADR-0008 · 全文检索索引

> 事件正文建 SQLite FTS5 trigram 索引，放在缓存目录，后台增量构建、跟随实时事件；修订 ADR-0001 中"不使用嵌入式数据库"一条。

状态：`accepted` · 更新：2026-10-09

## 背景

会话搜索（`docs/search.md`）只匹配标题、首条输入、cwd 等元数据。要按正文查"哪次对话修过缓存击穿""哪里出现过 `fn parse_releases(`"，就得检索消息、思考、工具参数和输出，并能跳到具体事件。约束：

- 中文没有空格分词，代码要按任意子串查，分词器只能按字符 n-gram。
- 本机 6557 个会话、源数据 17.7 GB（ADR-0002 记录时为 1.8 GB），引擎冷启动只读头尾（ADR-0002），不能为检索拖慢就绪。
- 只读 harness 数据；不新增生产依赖（依赖树里已有 bundled `rusqlite`）。
- 参考 Wake（MIT）：`messages_fts` 用 `fts5(... tokenize="trigram case_sensitive 0")`、`FTS_FORMAT` 换代全量重建、短词退化 LIKE、bm25 × 近因加权。Wake 不索引工具输出，我们索引。

## 决策

- **存储**：`uniflo_core::cache::dir()/fts-v1.sqlite`（macOS `~/Library/Caches/uniflo/`；设了 `UNIFLO_HOME` 时改到其下同样的相对位置）。WAL，`synchronous=NORMAL`。是 Uniflo 自己的派生数据，删掉后下次启动重建。
- **表**：`docs(id, sid, event, ts, pos, text, UNIQUE(sid, event))` + `docs_fts = fts5(text, content='docs', tokenize='trigram case_sensitive 0')`（外部内容，正文只存一份）+ `sess(sid, key, done_upd, done_pos, pinned, meta)` + `meta(tag)`。
  - 行号 `id = sid << 32 | seq << 3 | kind`：排序只读 FTS 索引就能拿到会话和 kind。实测在半建成的真实索引上，命中 1.4 万行时 JOIN `docs` 要 0.7 s（正文行很宽，每次 JOIN 都要读一页），只读索引 + bm25 为 10–60 ms。
  - `docs_fts` 由单行语句显式维护，不用触发器。触发器会开语句日志，也就是一个 savepoint，而 FTS5 每遇到 savepoint 都把待写词项刷成一个新段，相当于每条事件一个小段再加合并工作。实测去掉触发器后写入快 2.6–3 倍。
- **索引内容**：user / assistant 正文；reasoning（`[redacted]` 不入）；tool_call 的工具名 + 参数值（去掉 JSON 语法，截断 2 KB）；tool_result 输出截断 4 KB；system 只取 subtype。同一事件 id 再次出现时覆盖原行，partial 不留旧版本。
- **构建**：后台单线程（`uniflo-fts`）通过 `Engine::history` 按页（500 事件）从新到旧读取，每个会话一次 pass。会话按 `updated_at` 倒序处理，最近的会话先能检索到。
  - 节流：每页处理完后休眠，时长为该页耗时 × 0.5。
  - 写入合并进一个滚动事务，最多 500 ms 提交一次。每次提交都会让 FTS5 刷出一个新段；同一进程里 OpenCode / Hermes 等适配器读自家 SQLite 时会持有 SQLite 进程级 shm 锁，BEGIN/COMMIT 越频繁，等这把锁的时间越多。
  - 进度：`sess.done_upd`（pass 开始时会话的 `updated_at`）与 `done_pos`。重启后两者都没变的会话直接跳过；有变化的会话只从最新一页往回补，读到 `done_pos` 为止。
- **跟随**：写线程订阅引擎广播。`event` 按 id upsert，`removed` 删除该会话的行，新事件约 100 ms 内可检索。另外每 30 s（以及广播 lagged 时）按引擎会话表对账：摘要读取的事件不会广播，广播也可能丢，这些都由对账补上；对账时还会删掉引擎里已不存在的会话。
- **格式版本**：标签 `uniflo-fts/format{FTS_FORMAT}/uniflo{版本}/schema{SCHEMA_VERSION}`。与 `index-v1.json` 一样含 Uniflo 版本和 schema 版本，任一变化或文件不可读时整份删除重建（`/v1/stats` 的 `fts.rebuilt=true`）。
- **查询**：空白分隔的词按 AND 组合，每个词加引号作为子串，`"…"` 为短语，`-词` 为排除。少于 3 个字符的词（含排除的词）走 `LIKE`，此时结果按时间倒序。
  - 有短词时，不扫全表，而是按会话最后活动时间从新到旧逐个会话扫。只有短词时扫会话的整个行号区间（每 1024 行一条语句）；同时有长词时，先从 FTS 只取行号（不算 bm25、不读正文）并按会话分组，再对这些行逐行 `LIKE`。会话的 `updated_at` 是其事件时间的上界：凑够 `offset + limit` 个会话、且下一个会话的 `updated_at` 早于第 `offset + limit` 个会话的最新命中时，就可以停，这一页的结果是精确的；响应带 `scanned_until`，`total` 只是下限。用"早于"而不是"不晚于"：时间相同的会话可能在排序的 key 比较上胜出。
  - 扫描有 2 s 墙钟预算（`LIKE_BUDGET`），每条语句之间检查。超时就返回已找到的命中，并带 `partial: true`。
  - 混合查询原先是 FTS 全部命中 JOIN `docs` 再 `LIKE`，没有预算也不会提前停，本机 `fn main`、`async fn`、`if err`、`fn new` 要 8.5–18.7 s；改成上面的扫描后首次 55–324 ms、之后 32–73 ms，结果完整。
  - 排序：bm25 × `1 + 1/(1 + 距今天数/30)`，近因按会话 `updated_at` 计算（排的是"该翻哪场对话"）。按会话分组，每个会话最多 3 条命中，高亮区间用 `\u0002` / `\u0003` 标记。排序是全序：分数，再 `updated_at` 倒序，再会话 key；会话内按分数、再行号。分组用的 `HashMap` 每次遍历顺序不同，没有全序时同分的会话翻页会重复或漏掉，CLI 与 REST 的同一页也可能不同。
  - 片段从 `docs` 里存的正文截取，按 ASCII 大小写不敏感找检索词并高亮。FTS5 `snippet()` 每条命中都要重新执行一遍整个查询（每个 trigram × 每个段都要定位一次），只在正文里找不到检索词时才用它兜底（索引能折叠非 ASCII 大小写，如 `Ä`/`ä`）。
  - 一次查询只开一个读事务：扫描和所有片段读同一个快照。每开一次读事务都要拿 SQLite 进程级 VFS 互斥锁，而引擎的 SQLite 适配器打开数据库时会持有这把锁。实测在本机负载下，片段阶段 73% 的时间耗在等这把锁上。
  - `filter` 参数直接复用 `uniflo_search::search` 匹配会话，新增的会话过滤器（如 `is:archived`）自动生效。
- **接口**：`uniflo_search::fts::Fts`（库，嵌入方可用）；`GET /v1/search`、`events?around=`、`uniflo grep`；`--no-fts` 关闭，此时不创建文件，`/v1/search` 返回 503。
- **扩展**：`Fts::index_session` / `remove_session` 供不在引擎里的会话（如清理后的归档）写入或删除。这类会话标记为 pinned，对账与 `removed` 不会动它们。

实施状态：已落地（`crates/uniflo-search/src/fts.rs`、`fts/store.rs`、`fts/query.rs`、`crates/uniflo-gateway/src/search.rs`、`crates/uniflo-cli/src/grep.rs`、`crates/uniflo-core/src/window.rs`）。本机实测数据见 `notes/2026-10-09-worklog-fulltext-search.md`。

## 否决项

- `detail=none` / `detail=column`：索引能小很多，但对 trigram 来说每个 ≥4 字符的词都是多 token 短语。实测（bundled SQLite 3.50）短语 MATCH、`bm25()`、`snippet()` 都报 "phrase queries are not supported (detail!=full)"，只剩 `LIKE`，无法按规格排序和出片段。
- unicode61 等按词分词：中文整段会成为一个 token，查不到"缓存击穿"这样的子串；代码也只能做前缀匹配。
- 在引擎冷启动时顺带全文解析：会把 0.2 s 的就绪时间拖到分钟级（ADR-0002）。
- 每个查询现读 harness 文件（grep 式）：17.6 GB 源数据，单次查询要数十秒。
- tantivy 等独立检索库：新增生产依赖，体积大，还需要自己做 CJK 分词。

## 后果

- 收益：中文和代码子串检索，命中可以直接跳到事件；嵌入方、网关、CLI 共用同一个库实现，后续的接入方（如 MCP）直接复用 `Fts::search` 与同一份响应类型。
- 代价：
  - 磁盘占用约为源数据的 0.32 倍（本机 5.6 GB / 17.7 GB）。trigram 索引约为被索引文本的 2.4 倍，正文另存一份。
  - 首次全量构建约 14 分钟（本机 134 万事件，机器负载 15–22 时测得）。
  - 查询（≥ 3 字符的词）：本机 p50 18 ms、p95 69 ms。
  - 只有短词的查询：常见词（本机命中 1400–3900 个会话）在凑够一页时就停，热缓存下 21–79 ms，冷缓存首次最多约 1 s。罕见词扫满 2 s 预算后返回 `partial`，本机 2 s 约能往回覆盖 13–28 天的会话。完整扫一遍全部存储正文（约 1.4 GB）要 15–55 s，瓶颈在 IO。规格要求这类词走 LIKE，本次不另建 bigram 索引。
  - 标签含 Uniflo 版本，每次升级都会重建一次。
  - 同一个缓存目录只应由一个守护进程写入：不同版本的守护进程会互相把对方的标签判为不匹配并重建。
- 同步：`docs/api.md`（`/v1/search`、`around`、`/v1/stats.fts`）、`docs/search.md`（全文检索语法）、`docs/schema.md`（响应类型）、`docs/architecture.md`（数据流与 `search → core` 依赖）、ADR-0001（修订）、ADR-0002（复议触发）。

## 复议触发

- 索引大小或首建时间成为用户痛点（例如要求按 harness / 项目开关索引，这是本次的非目标），或升级时重建不可接受：届时考虑把 Uniflo 版本移出标签，只认 `FTS_FORMAT` 与 schema 版本。
- 需要语义检索或拼写容错：届时再引入向量或其他检索引擎。
