# 运行可靠性规格

Uniflo 在 Windows、Linux、macOS 上只读读取 harness 会话，将结果提供给 REST、网页、CLI 和 MCP；派生缓存不得因多个消费者存在而丢失内容或持续竞争写入。

## 全文索引

- 一个索引文件的后台写入有明确所有权；守护进程、嵌入式使用和 MCP 进程内回退不能同时不协调地修改同一索引。
- 已有搜索内容在正常更新和其他消费者连接时仍然可检索。
- 暂态写入失败不能静默丢弃显式接收的索引请求，不能把尚未提交的内容标记为完成。
- 冷热分层、版本就地刷新、旧格式迁移、子串与中文查询、归档会话 pinned 语义保持不变。
- 不通过清空用户真实索引、吞掉全部错误或无限重试隐藏根因。

## 跨平台

- 进程探测、路径监听、安装升级、终端恢复必须正确处理平台差异；只修复本轮经可复现证据确认的缺陷，不添加无关功能。
- 平台验证与跨平台单测、CI、真实机器验证分别记录，未执行项不得写成通过。
- 不修改真实 harness 数据、全局配置、真实安装或系统服务来运行测试；所有写入在隔离目录中。

## 资源占用

- 守护进程长期驻留时的常见情况（数千个会话、若干会话正在写入）下，内存只保留回答请求和推送所需的数据，批量建索引的临时数据用完即释放；稳定后的 footprint 不超过 0.2.3 在同一份数据上的一半。
- 没有新写入时不轮询文件或目录，5 分钟平均 CPU 低于 0.5%；有写入时只读取变化的部分，不对全部会话做克隆或全量扫描。
- `uniflo mcp` 默认是连守护进程的薄客户端，常驻时占用很小。连不上守护进程时才在进程内建索引；守护进程恢复后释放这份索引，进程内不运行常驻的全文索引写入和目录监听。
- 达不到上述目标时，写明实测值和原因，不得只报通过。

### Scenario: 守护进程稳定占用
- GIVEN 0.2.3 安装版与 0.2.4 构建版，各自使用隔离的 data 和 cache 目录读取同一份真实数据
- WHEN 两者都完成首次扫描和用量账本、运行 10 分钟后，测量 footprint，再测 5 分钟 CPU（`ps -o time` 增量）
- THEN 0.2.4 的 footprint 不超过 0.2.3 的一半，并记录有实时写入时两者的 CPU
- AND 只输出计数、大小和耗时

### Scenario: 空闲能耗
- GIVEN 一份数千个会话的合成数据，守护进程已建完索引，期间没有任何写入
- WHEN 连续观察 5 分钟
- THEN 平均 CPU 低于 0.5%，`sample` 中没有周期性的全量目录扫描或会话克隆

### Scenario: MCP 回退后释放
- GIVEN 守护进程未运行时启动的 `uniflo mcp`，已用进程内索引回答过一次请求
- WHEN 启动守护进程后再发一次请求
- THEN 回答来自守护进程，进程内索引被释放，`uniflo mcp` 的 footprint 回落到薄客户端水平

## 验证与发布

- 每个已修复缺陷保留可重放的消费者可见红绿证据，统一门禁与网页 e2e 通过。
## 工作中会话排序

- 工作中队列按本轮进入 work 状态的时间升序排列，同时间用稳定键确定顺序，不使用最近回复时间或会话最初创建时间。
- 子代理同样排序。只有子代理在工作的父家族以最早进入 work 的活动成员进入队列；家族持续有工作成员时保持队列位置。
- 回复、元数据、费用更新、加载更多、重连和刷新不应改变仍在同一工作轮次里的顺序；退出工作后再次进入排在当前队列后面。
- 空闲列表保留最近活动优先；筛选结果的相关度与父子层级保持原契约。

- 已发布版本不可覆盖。本轮新补丁版本在用户明确确认后发布，发布说明列出根因、影响、修复和验证边界。
- 正式发布同步 GitHub Release、7 个 crate、5 个平台包及 SHA256SUMS、官网和仓库文档，验证线上返回与版本相符。
