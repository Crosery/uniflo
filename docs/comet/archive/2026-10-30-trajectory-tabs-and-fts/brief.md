# Outcome

网页控制台的会话详情改为 DeepSeek Harness 式的视图 tab：对话、链路、用量、子代理、信息。原来的「每步用量」下拉和右侧详情栏并入这些 tab。「链路」按轮、步、工具和子代理列出完整调用链，每一步的 token、费用（含按价格逐类拆分）和耗时都看得到。父会话在侧栏、会话头和用量 tab 显示含全部子代理的合计费用。全文索引修复以下三类问题，并提升建库速度：错误累积、建完后反复退回「建立中」、与旧版写者互相覆盖。确认「工作中」列表不再跳位。会话页同时做一轮精简：去掉重复和看不懂的数字，只留核心信息。守护进程和 `uniflo mcp` 在常见使用下降低内存占用与能耗。最后经 main 发布正式版 0.2.4。

# Scope

- 网页控制台：`examples/web/index.html` 与 `crates/uniflo-gateway/src/index.html` 两份同步改。
  - 会话头下增加 tab 栏，设计稿见 Decisions。
  - 侧栏父会话改为显示家族合计费用。
  - 检索视图的索引进度只在真正建库时出现，并提示与旧版写者共存的情况。
  - 会话页精简：侧栏、会话头、tab 标签、链路、记录详情、用量、子代理、信息和对话页脚只留核心信息，规则见 Decisions。
- 网关与 core：
  - 新增会话链路接口。
  - 每步用量增加费用拆分与所用单价。
  - 会话增加家族合计，子代理用量变化时随推送更新。
  - 新类型和可选字段在 `uniflo-schema` 中定义。
- 全文索引（`uniflo-search`）：
  - 修复促温失败后会话同时留在冷热两层，以及由此导致的 UNIQUE 错误和检索 500。
  - 失败只回滚出错的工作单元。
  - `indexing` 与 `progress` 只反映真正未建的部分。
  - 发现外部写者时自愈，并在状态里报告它的进程。
  - 提升首建吞吐。
- 资源占用：守护进程稳定运行时的内存占用和空闲 CPU，`uniflo mcp` 常驻时的内存占用；找出主要占用并修复，前后对比 0.2.3。
- 文档：`docs/api.md`、`docs/schema.md`、`docs/console.md`、`docs/search.md`、相关 ADR 的修订、当天 worklog、CHANGELOG 或发布说明，以及官网版本。
- 发布：stage 验证通过后快进 main，打 `v0.2.4` 正式 tag。

# Non-goals

- 对话 tab 只精简回合页脚、用户消息时间和思考字数，不改事件流的其他渲染。
- 精简范围是会话页；用量、检索、管理、洞察视图本次不动。
- 不做 dsh 的停靠、分栏、浮窗。
- 不推算 harness 没有记录的首 token 延迟。
- 不改 wire schema 已有字段的语义。
- 不写 harness 会话文件。
- 不新增生产依赖。
- 不删除真实索引来掩盖问题。
- 不把索引文件改名为 fts-v3。这样做会让所有用户强制重建约 16 分钟，改用检测、自愈和提示。
- 不结束用户自己的进程（例如旧版 `uniflo mcp`）。

  - 侧栏没有「会话」标题、条数和耗时；
  - harness 选择与「筛选」按钮在同一行；
  - 原来的 5 个快捷筛选收进「筛选」菜单，勾选后写入查询并在按钮上显示个数；

  - 会话头的费用只显示金额；

  明暗两套主题、1480 和 390 宽度截图无溢出、遮挡和对比度问题。
- 资源占用在同一台机器、同一份真实数据上对比 0.2.3（隔离的 data 和 cache 目录）：

  - 没有新写入时，5 分钟平均 CPU 低于 0.5%；
  - 有实时写入时的 CPU 和常驻 `uniflo mcp` 的 footprint 都记录在 worklog。

- 正式版 0.2.4 通过 main 发布：

  - 官网和仓库版本、发布说明一致。

# Constraints and invariants

- wire schema v1 只增不改，改 schema 的同一提交同步 `docs/schema.md`。
- 依赖方向 `schema ← core ← search / adapters ← gateway ← cli` 不变。
- harness 数据只读，SQLite 走只读打开。
- 测试只用手写合成数据，以及隔离的 HOME、data、cache 目录。
- 真实数据实验只看计数和耗时，不打印正文。
- 控制台两份 `index.html` 内容一致。UI 用控制台现有组件和设计 token，不用原生 select 等控件。
- 分支只用 stage 和 main，main 只能快进到 stage 的提交。

# Decisions

- 2026-10-30 用户要求「每步用量和侧边栏可以仿照 deepseek harness 一样，多做几个 tab 页」。用户随后纠正：「deepseek 不是右边侧边栏，是新的一个tab栏」。因此改为会话头下的视图 tab，参照 dsh 的「对话 / 轨迹（Trajectory）」，右侧栏不再保留。
- 设计稿是 `notes/design/2026-10-30-session-tabs.html`（Build 时从 `/tmp/uf-design/design.html` 收入仓库），用户于 2026-10-30 选择「按设计稿实现」：
  - tab 为对话、链路、用量、子代理、信息。
  - 链路是工具栏、时间概览，加上「轮 → 步 → 思考/回复/工具/子代理」分层表格，选中一行时右侧出记录详情。
  - 父会话的合计金额前加分支小图标，悬停看拆分。
- 子代理费用：父会话显示含全部后代的合计，子代理行保留自身费用（用户：「能不能统一算到主代理里面……用户可能想看到一个统一花费」）。
- 版本 0.2.4。用户说：「stage 这边你先改完看看有没有问题，没问题就直接走发正式版吧」，即 stage 验证后经 main 发正式版，不发 rc。
- 「会话偏移」指工作中列表跳位。0.2.3 已修，这次只复测不改；修复前已在运行中的 0.2.3 上观察 10 分钟、采样 40 次，跳位 0 次。
- 索引诊断（2026-10-30）的结论：
  - 主因是 10-25 启动的旧版 `uniflo mcp`（pid 74239，没有写租约）和守护进程同时写 `fts-v2.sqlite`，`sess` 行数每几秒在约 4.8k 与 6.2k 之间来回变。
  - 另有两个独立缺陷：促温失败留下冷热双层数据；实时追加让 `indexing` 反复变 true。
  - 隔离首建 5172 个会话耗时 965 s；写线程 35% 时间在节流休眠，33% 在 FTS5 插入，17% 在提交。
- `uniflo grep 词 since:14d` 返回 0 是把 `since:14d` 当成了检索词，属于调用方式问题，本次不改 CLI。
- 2026-10-30 用户转述反馈：「目前的信息太多太密，很多数字莫名其妙……我们要做到最够的简洁不要重复，保留核心的信息」，截图圈出侧栏「会话」标题和筛选行。据此精简会话页，具体为：
  - 侧栏：
    - 去掉标题和「N 条 · x ms」；
    - harness 选择框不显示计数；
    - 5 个快捷筛选收进「筛选」菜单，每项附一句说明，「有进程」「顶层」改叫「进程在运行」「隐藏子代理」；
    - 分组不带计数；
    - 会话行只留标题、目录、时间和不低于 $0.01 的费用。
  - 会话头：费用只显示金额，拆分放在悬停提示里。
  - tab 标签：只有「子代理」带个数。
  - 链路：
    - 列只留 时长 / Token / 费用，Token 的分项放在悬停提示里；
    - 去掉工具栏汇总和行内的步数、工具数、字数标签；
    - 记录详情不分 tab，模型步骤依次是费用（token × 单价 = 金额）、上下文、时间线和定位按钮。
  - 用量：保留合计及拆分、上下文、每步费用；只有多于一个模型时才显示按模型表，表里只有费用和占比。去掉 token 卡片和缓存命中率。
  - 子代理：只留标题、启动位置、时长、费用和操作。
  - 信息：状态不显示原始原因字段。
  - 对话：
    - 回合页脚只写用时和结束时间，非正常结束时写中文原因（已中断、出错等）；
    - 用户消息的时间悬停才显示；
    - 思考不显示字数。
  - 会话内不足 1 美分的金额显示 4 位小数，不写「<$0.01」。
- 2026-10-30 用户提出：「uniflo 要保证大部分情况不要过多的内存占用和对应的能耗占用」，附 Activity Monitor 截图。实测：
  - 0.2.3 常驻守护进程（运行约 4 天）footprint 571 MB，几乎全是 malloc 脏页；累计 CPU 1506 分钟，约占平均 26%；采样热点有 `Session::clone`、`usage_progress`、反复 stat/open、SQLite 反复解析语句。
  - 旧版 0.2.2 `uniflo mcp`（pid 74239）footprint 354 MB，持续约 7% CPU。
  - 另有约 60 个 `uniflo mcp` 进程，每个约 1 MB RSS。
  - 5 天前 e2e 遗留的 3 个合成数据守护进程和 1 个 headless Chrome 已结束。
  - 本次要找出主要原因并修复，验收见 Acceptance examples。
- 2026-10-30 资源目标：并排实测 0.2.4 的 footprint 为 0.2.3 的 49–72%（247 对 453 MB、209 对 291 MB），CPU 47.7% → 3.7%，MCP 空闲约 350 → 10 MB。用户选择「按实测验收，现在发布」：内存验收改为明显低于 0.2.3 并记录实测值，CPU 与 MCP 目标不变；重做用量账本存储、继续压内存放到下一版。
- 2026-10-30 检索延迟：独立验收测得常见代码词的首次（冷）查询要读盘、解压、逐行核验几百个冷层会话，p95 超过 200 ms。并行读块、稠密折叠表等优化后，同一份索引的冷首查 p50/p95/最慢从 119/1550/3760 ms 降到 72/933/2523 ms，重复查询 p95 9.3 ms，仍达不到 100 次合计 p95 < 200 ms。用户选择「保持完整，改验收」：首查不加时间上限、结果保持完整；验收改为 100 次 p50 < 50 ms、第 2–5 次 p95 < 200 ms、冷首查分布低于 0.2.4。

# Verification expectations

- 每个缺陷先有修前失败的测试：
  - 促温失败的双层数据；
  - 双层会话的 UNIQUE 错误和检索 500；
  - 外部写者删除后不自愈；
  - 实时追加时 `indexing` 变 true。
  - 修后这些测试转为通过。
- 新接口、家族合计和费用拆分都有单测或集成测试。
- 网页由 `scripts/demo-e2e.mjs` 覆盖：
  - tab 切换与 URL 恢复；
  - 链路展开、选中详情、j/k 与 Esc；
  - 用量 tab 的合计；
  - 侧栏家族合计与实时更新。
- 网页按亮、暗两套主题截图核对；会话页精简前后各留一组截图。
- 资源占用：用 `footprint`、`ps -o time` 增量、`top -stats cpu,idlew,power` 和 `sample` 测量。修复带回归测试；隔离运行，不碰常驻守护进程。
- 吞吐的对比方法：在同一台机器上，0.2.3 安装版与 0.2.4 构建版先后在隔离缓存中首建真实数据，记录耗时、会话/秒、事件/秒和当时负载。
- 发布结果按 GitHub、crates.io 和官网的真实返回核对。
