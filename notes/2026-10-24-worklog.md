## 3. `install.ps1` 在中文 Windows 上解析失败、提示乱码

- 证据（LuoXi，Windows 11，PowerShell 5.1，代码页 936）：
  - `powershell -File install.ps1`（脚本头注释里写明的用法）直接报 `The string is missing the terminator`，exit 1，什么也没装。
  - `irm … | iex` 能装上，但中文提示全是乱码。
  - GitHub 返回该资产时 `Content-Type: application/octet-stream`，`Invoke-WebRequest` 拿到的 `Content` 是 `System.Byte[]`。
- 根因：
  - PowerShell 5.1 按 ANSI 代码页读取没有 BOM 的 `-File` 脚本：UTF-8 中文被当成 GBK 解码，字符串结尾的引号被吞掉，于是解析失败。
  - `irm` 把 octet-stream 按 Latin-1 解码，所以中文显示成乱码。
  - 加 BOM 不可行：BOM 在 Latin-1 解码下会变成 `ï»¿` 前缀，反而弄坏 `irm | iex`。
- 改动：
  - `scripts/install.ps1` 改为纯 ASCII：15 条中文提示改成 `\uXXXX` 转义，由 `T` 函数（`[regex]::Unescape`）在运行时还原，再用 `-f` 填参数（路径不经过 Unescape）。用户看到的文字不变。
  - `scripts/check-dist.mjs` 加检查「`install.ps1` 不得含非 ASCII 字节」，挂在 `scripts/verify.sh` 的打包检查里。
  - 红：`scripts/install.ps1 non-ASCII on lines 22,25,…,136`。绿：`release packaging: 5 targets, binstall templates match, aarch64-apple-darwin package layout ok`。
  - 逐段解码后比对：旧文件里 33 段中文全部原样还原。
- 坑：用 Edit 工具写入的 `\uXXXX` 被编辑后钩子还原成了中文；改用脚本直接写文件，再以 `check-dist` 确认。
- Windows 实机复验：见 §4。

## 5. macOS 验收发现的两个问题

### `install.sh` 用 macOS 的 `/bin/sh` 一跑就退出

- 复现：
  - `env -i LANG=en_US.UTF-8 /bin/sh -c 'set -u; version=1; echo "a $version（b"'` 输出 `/bin/sh: version�: unbound variable`，exit 127。
  - 不带 `LANG` 时正常。
  - macOS 15.8.1 的 `/bin/sh` 是 bash 3.2.57。
- 根因：bash 3.2 在 UTF-8 语言环境下，把未加花括号的 `$var` 后面紧跟的多字节字符的部分字节读进了变量名，`set -u` 随即报错退出。
  - 第 78 行的 `"下载 uniflo $version（$target）"` 每次安装都会执行，所以 macOS 上用 `curl … | sh` 必定失败。
  - 测试用 `env_clear()` 清掉了 `LANG`，一直在 C 语言环境下跑，所以没测出来。
- 改动：
  - `scripts/install.sh` 里 7 处紧跟中文标点的 `$var` 都改成 `${var}`；`git ls-files '*.sh'` 下已没有同类写法。
  - `crates/uniflo-cli/tests/dist.rs` 的 `Machine::cmd` 设 `LANG=en_US.UTF-8`，和真实终端一致。
  - 红：`install_script*` 3 个测试失败。绿：`cargo test -p uniflo --test dist` 5 passed。
  - `env -i LANG=en_US.UTF-8 /bin/sh scripts/install.sh --bogus` 输出完整的中文错误，exit 1。

### Windows 上 `daemon --restart` 让捕获输出的调用方一直等

- 现象：Windows 验收里，经 wanctl 执行 `uniflo daemon --restart` 一直不返回。
- 证据（LuoXi，官方 beta.3，独立目录，端口 7466）：用 .NET `Process` 重定向 stdout/stderr 启动 `daemon --restart`，输出 `restart: exited=True code=0 pipes_closed_within_5s=False`，此时 health 返回 200；执行 `daemon --stop` 后才变成 `pipes closed within 5s: True`。
- 根因：
  - Windows 上 `std::process::Command` 以 `bInheritHandles=TRUE` 创建进程。父进程自己的 stdout/stderr 如果是调用方的管道，句柄本身可继承，就会一起被后台守护进程继承。
  - 调用方要等到守护进程退出才收到 EOF。脚本、CI、harness 钩子都会卡住。
  - Unix 上 Rust 默认给文件描述符设 CLOEXEC，没有这个问题。
- 影响：`daemon --restart`，以及 Windows / Linux 上 `uniflo update` 之后经 `spawn_detached` 的自动重启（Windows 才会卡）。在交互式控制台里使用不受影响。
- 改动：
  - `uniflo_core::util::stdio_not_inheritable()`：用 `SetHandleInformation` 清掉本进程 std 句柄的 `HANDLE_FLAG_INHERIT`。
  - `spawn_detached` 在 Windows 上 spawn 前调用它。
  - 工作区 `windows-sys` 加 `Win32_System_Console` feature，不是新依赖。
- 测试：新增 `crates/uniflo-cli/tests/daemon.rs` 的 `restart_returns_and_releases_the_callers_pipes`：用管道捕获输出执行 `daemon --restart`，要求进程退出后 10 s 内两条管道都收到 EOF，再 `--stop`。
  - macOS：通过（Unix 本来就没问题）。
  - Windows（LuoXi，源码加补丁，`cargo test --release -j 2 -p uniflo --test daemon`）：
    - 红：`stdout stayed open after daemon --restart exited`，用时 20.99 s 后失败。
    - 绿：`1 passed`，1.68 s。
  - 补丁版二进制在 LuoXi 上实测：`restart: exited=True code=0 pipes_closed_within_5s=True`，health 返回 200，`--stop` 后端口 7467 已释放。
- 同一个补丁版二进制在 LuoXi 上扫真实数据：`sessions=19884 sources=23957 bad_lines=0 read_errors=0 unknown={}`（beta.3 时还有 ghost_snapshot 38 条）。
